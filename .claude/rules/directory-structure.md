# ディレクトリ構成

ExecDBは「`engine`ライブラリが核、現行のスタンドアロン実行ファイル
（REPL＋外部I/F＋バイナリ内蔵）はそのライブラリを使った1つのアプリケーション」
という構造を取る（仕様書§6参照）。新しいファイルを追加する際は、必ずこの
構造のどちらに属するかを意識すること。

```
execdb/
├── CLAUDE.md               ← プロジェクトルール（参照先の案内）
├── PLAN.md                 ← 実装計画・進捗管理（開発フェーズ、現在地、保留事項）
├── Makefile
├── LICENSE                 （MIT）
├── go.mod
├── go.sum
├── .gitignore
├── README.md               ← クイックスタート（英語）
├── README_ja.md            ← クイックスタート（日本語）
├── docs/                     ← 利用者向けドキュメント（フェーズ④完了後、Step 9/10で新設）
│   ├── spec/                   ← execdb_spec.md（開発者・高度な利用者向けの設計・仕様書）
│   ├── usage/                   ← CLIコマンド・オプションのリファレンス
│   ├── examples/                 ← 実例集（CI/CD、スナップショット共有、モックAPI等）
│   └── tour/                     ← ExecDB入門（体験型ガイド、実装完了後に作成予定）
├── .devcontainer/
├── .vscode/
├── .claude/
│   ├── settings.json
│   └── rules/
├── engine/                 ← 【ライブラリ本体】インメモリSQLエンジン
├── cmd/execdb/             ← 【アプリ】engineを利用した単一バイナリRDBMSの実装
├── tests/                    ← `make test` が実行するE2E/結合テスト一式
└── .github/workflows/       ← CI定義（test.yml, release.yml 等）
```

`engine/`・`cmd/execdb/` 配下の具体的なファイル構成（`engine.go`, `persist.go`,
`main.go`, `repl.go`, `pgwire.go` 等）は、実装を進めながら決めてよい。ここでは
「どちらのディレクトリに属するか」という配置の判断基準のみを定める。

## 配置の判断基準

- **ネットワークI/Fに一切触れないコード** → `engine/`
- **REPL・外部I/F・アクセス制御・CLIオプションなど、`engine`を使う側のロジック** → `cmd/execdb/`
- `engine`パッケージから `net`/`net/http` 等への依存を追加しないこと
  （§6の「ネットワークI/Fを持たないことによる安全性」という設計原則を壊すため）。

## 各ファイル・ディレクトリの補足

- **go.sum**: リポジトリにコミットする。依存パッケージのハッシュ値による
  改ざん検知・再現可能なビルドを担保するファイルであり、`go.mod` とセットで
  コミットするのがGoの標準的な慣習。除外しない。
- **README.md / README_ja.md**: 英語版・日本語版を両方用意する。仕様の詳細
  ではなく、インストール・最初の一歩に絞ったクイックスタートに徹し、
  詳細は`docs/`配下の各ドキュメントへリンクする（フェーズ④完了後、Step 9で
  この方針へ書き直した——それ以前は開発初期のプレースホルダのままだった）。
- **.devcontainer/**: 開発コンテナ定義（`devcontainer.json` 等）。
- **.vscode/**: エディタ設定（推奨拡張機能等、チームで共有したい設定のみ）。
- **docs/**: 利用者向けドキュメント一式（フェーズ④完了後、Step 9/10で新設。
  4つのディレクトリに分かれ、対象読者・目的が異なる）。
  - **docs/spec/**: `execdb_spec.md`（開発者・高度な利用者向けの設計・仕様書。
    元はリポジトリ直下にあったが、Step 9で移動した——`CLAUDE.md`が指す
    「実装しながら育てるドキュメント」という役割自体は変わらず、単に置き場所を
    変えただけ。`.claude/rules/`側からの`execdb_spec.md§N`という節番号での
    引用は、移動後もファイル名ベースの慣習的な引用のままでよい）。
  - **docs/usage/**: CLIコマンド（起動オプション）・REPLドットコマンドの
    リファレンス。仕様書（`docs/spec/`）が設計判断の理由まで説明する散文なのに
    対し、こちらは「今すぐ使うための」テーブル中心の索引的なドキュメント。
  - **docs/examples/**: 実例集（CI/CDでのInstant Test DB、`.snapshot`による
    バグ再現共有、外部I/F経由のモックAPIサーバー、SQL学習サンドボックス等。
    仕様書§5の各ユースケースを、実際に打つコマンド付きで肉付けしたもの）。
  - **docs/tour/**: 実装が完了してから作成する入門ガイド（体験型、順を追って
    学ぶ形式）。Step 10で着手予定、Step 9の時点ではまだ存在しない。
- **tests/**: `.claude/rules/testing.md` の `make test` が実行するE2E/結合
  テスト一式（`e2e.sh`、他言語ドライバ確認用の `pgclient`・`drivers/` 等）。
  **`docs/examples/`とは役割が異なる**——`tests/`はCIが自動実行する検証専用、
  `docs/examples/`は人間が読んで手元で試すための実例集（フェーズ④完了時点で
  保留にしていた「ユーザー向けサンプルをどう用意するか」という論点に対する
  Step 9での回答）。
- **配布物（各OS向けビルド済みバイナリ）**: リポジトリに直接コミットしない
  （詳細は `.claude/rules/distribution.md` 参照）。

# テスト方針

## 開発環境の前提

開発者の手元環境は**Linuxのみ**。Windows/macOSでの実際の動作確認は、手元では
行わず GitHub Actions（`windows-latest`/`macos-latest` 等のホステッドランナー）
に委ねる。パブリックリポジトリ（MITライセンス）のため、GitHub Actionsは実質
無制限に利用できる。

| 対象 | 進め方 |
| :--- | :--- |
| コアロジック（`engine`パッケージ、フッター読み書き、`.overwrite`のrename退避方式等） | まずLinux環境・Goのみで開発し、ロジックの正しさを固める。フィードバックループを最速に保つ。 |
| クロスプラットフォーム動作確認（Windows/macOS） | 開発初期からGitHub Actionsで自動テストを組み、都度確認する。特に`.overwrite`はWindows特有のOS制約（`ERROR_SHARING_VIOLATION`等）が設計に直結しているため、後回しにせず早期から継続的に検証する。 |
| PostgreSQL互換ワイヤープロトコル | まずGo（`pgx`等）で作りきる。他言語ドライバでの検証はプロトコル実装が固まった後にまとめて行う。 |
| 依存ライブラリの脆弱性・ライセンスチェック | GitHub Actions上で `trivy` を実行し、既知の脆弱性（CVE）とライセンス互換性（MIT/BSD/Apache-2.0等は許可、GPL系等は拒否）をチェックする。ソースコード自体のコピペ検出は対象外（人間レビューに委ねる）。 |

## 実装後の動作確認について

実装したら、必ずビルド確認（`make build` 等。詳細は `PLAN.md`
の「保留事項」参照）に加えて実際の動作確認を行うこと。ロジック上正しそうに
見えても、実際に動かして初めて見つかる不具合は起こりうる。

- ビルド確認（`make build`）は`.claude/settings.json`の`PostToolUse`フックで
  `.go`/`go.mod`/`go.sum`編集時に自動実行される（フェーズ①Step 1で設定済み）。
  `make test`（e2e、数十秒かかる）はフック化していないため、引き続き手動で
  判断して実行すること。
- `make test`（`examples/` を通した実動作確認）を走らせる粒度は、作業規模に
  応じて判断する。
  - 小規模な修正（数行の変更、1関数内で完結する変更）は、一連の作業が終わった
    最後に1回でよい。
  - 大規模な変更（複数ファイルにまたがる、設計に関わる変更）は、各ステップの
    区切りごとに実行すること。
  - 判断に迷ったら、実行する側に倒すこと。

## `examples/e2e.sh`（`make test`）実装時の落とし穴（フェーズ①Step 5）

- **`.overwrite`を伴うテストは、`bin/execdb`本体ではなく必ずコピーに対して
  実行する。** `.overwrite`は対象ファイルの中身を書き換えるため、ビルド
  成果物そのものに対して実行すると、次の`make build`まで壊れた状態が残る。
- **バックグラウンドサーバーのPIDを`pid=$(start_server ...)`のように
  コマンド置換で受け取った場合、そのPIDは呼び出し元シェルの「子プロセス」
  ではなくなる（コマンド置換はサブシェルを生成するため）。** そのPIDに対して
  bashの`wait`組み込みコマンドを使うと`wait: pid ###: not a child of this
  shell`で失敗する（`2>/dev/null`で隠しても`set -e`下では地雷になりうる）。
  代わりに`kill -0 "$pid"`をポーリングして「プロセスが消えるまで待つ」方式を
  使うこと（`kill -0`は親子関係を問わず任意の可視PIDに使える）。
- **`set -e`（errexit）下で、`out="$(コマンド)"`のようなコマンド置換への
  代入は、内部コマンドが非ゼロで終了すると代入文自体が失敗扱いになり
  スクリプトが即終了する。** `psql -c`はSQLエラー時に非ゼロを返すため、
  エラーメッセージを検証したいテストでは`out="$(psql ... 2>&1 || true)"`の
  ように内側で明示的に握りつぶす必要がある（`grep -q`とのパイプに
  `pipefail`が絡むケースも同様に要注意）。
- **バックグラウンド起動したサーバーモード（`-n`）プロセスは、終了シグナルを
  受けると`--snapshot-as`未指定ならバイナリ名でカレントディレクトリに
  自動保存する。** テストスクリプトの実行時カレントディレクトリのまま
  バックグラウンド起動すると、リポジトリ直下にファイルが生成されてしまう。
  起動時に`(cd "$WORK" && exec "$@")`のようにサブシェルで作業ディレクトリを
  一時ディレクトリへ切り替えてから`exec`すること（`exec`で置き換えないと
  `$!`がサブシェルのPIDになり、シグナル送信・生存確認の対象がずれる）。
- **`fail()`で`exit 1`する設計だと、それより前で起動済みのバックグラウンド
  サーバーが`stop_server`を呼ばれないまま孤児プロセスとして残り、次回以降の
  実行でポート/ソケットが衝突する。** 起動したPIDを配列に記録しておき、
  スクリプト全体の`trap ... EXIT`で無条件にkillする「安全網」を、個別の
  `stop_server`呼び出しとは別に必ず用意すること。

## GitHub Actions CI設定時の落とし穴（フェーズ①Step 5、初回push後に発覚）

`.github/workflows/test.yml`を初めてpushした際に実際にCI上でのみ顕在化した
不具合。手元（Linux）では再現しない種類の問題なので、ここに記録しておく。

- **`Makefile`やシェルスクリプトで`/dev/stderr`等のUnix固有デバイスパスに
  依存する記述は、Windowsランナー（Git Bash/MSYS環境）で壊れる。** 例:
  `gofmt -s -l . | tee /dev/stderr`は`tee: /dev/stderr: No such file or
  directory`で失敗した。`tee`を使わず、出力を変数に受けてから
  `echo "$var" 1>&2`のように標準の重定向だけで書き直すこと。
- **Windowsランナーのgit checkoutはデフォルトで`core.autocrlf=true`相当の
  挙動になりうるため、`.go`ファイルがCRLFで展開され、`gofmt -l`
  （LF前提）が全ファイルを「未整形」と誤検知する恐れがある。** 上記の
  `tee`問題を直しただけではこの誤検知を踏む可能性が残るため、リポジトリ
  ルートに`.gitattributes`（`* text=auto eol=lf`）を置き、チェックアウト時の
  改行コードをプラットフォームによらずLFに固定すること。
- **GitHub Actionsの`uses: owner/repo@TAG`は、実際のリリースタグ名と
  厳密に一致しないと`Unable to resolve action`で失敗する。** 特に`v`
  プレフィックスの有無を見落としやすい（例:
  `aquasecurity/trivy-action@0.36.0`ではなく`@v0.36.0`が正しいタグ名
  だった）。ワークフローに書く前に`curl -sf
  https://api.github.com/repos/<owner>/<repo>/releases/latest`等で
  `tag_name`の正確な文字列を確認すること。
- **Windowsには`chmod`による実行ビットという概念が無い。** ファイルの
  実行可能性は拡張子（`.exe`/`.bat`/`.cmd`等）でのみ判定されるため、
  `os.Chmod(path, 0o755)`を呼んでも、その後`os.Stat(path).Mode().Perm()`
  で実行ビット（`0o100`等）を確認するテストはWindowsで失敗する
  （常に`-rw-rw-rw-`相当になる）。「拡張子を含まないファイル名に対して
  chmodで実行可能にした」という状態をテストで検証したい場合は、
  `runtime.GOOS != "windows"`でそのアサーションだけガードすること
  （`GOOS=windows`への単純なクロスビルドではこの種の実行時アサーション
  の誤りは検出できず、実際にWindowsランナー上で`go test`を走らせて
  初めて発覚する）。

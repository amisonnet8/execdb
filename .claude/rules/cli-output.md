# CLI出力

## 言語

REPLのメッセージ、エラーメッセージ、`--help`、ログ出力等、CLIが出力する文字列は
**英語**とする。国際的なOSSとしての公開・利用を想定しているため。

（この対話・チャット上でのコミュニケーションは日本語で行うが、コード・コメント・
CLI出力は英語で書くこと。両者を混同しないこと。）

## 出力スタイル（SQLite CLIを参考にする）

ExecDBのREPLコマンド体系は SQLite CLI（`sqlite3`）を踏襲している
（`directory-structure.md`/仕様書§3参照）。コマンド名だけでなく、**実際の
出力内容・フォーマットも `sqlite3` を参考にする**とよい。例えば `.tables` の
一覧表示の並び方、`.schema` の出力形式、クエリ結果を表示する際の列揃え・
区切り方など、迷ったら `sqlite3` コマンドの挙動を確認し、大きく外れない
出力にすること。独自の書式を新たに考案する前に、まず本家の出力を確認する。

**色付け・罫線・TUI等の装飾ライブラリは導入しない。** `sqlite3` 自身も装飾を
最小限に抑えたプレーンテキスト出力であり、CI/CDでのパイプ処理・スクリプト
利用（§5のユースケース1, 4等）との相性を優先する。また `fatih/color` 等の
軽量なものはともかく、`bubbletea` 等のTUIフレームワークは依存関係を含めて
バイナリサイズを増大させ、「単一バイナリ完結・軽量」というコアコンセプト
（§1）と衝突するため、標準出力の範囲で完結させること（実行ファイルサイズ
全般の方針は `binary-size.md` 参照）。

## 出力モード（`.mode`/`.headers`、フェーズ③Step 2）

`.mode`は`list`（既定）/`column`/`csv`/`json`/`line`の5種のみを採用する。
`quote`/`insert`/`tabs`/`markdown`/`box`/`html`等の装飾系モードは、上記
「出力スタイル」節の方針（装飾を最小限に、CI/CDでのパイプ処理を優先）に
より不採用（増やす場合はまず`execdb_spec.md`§3を更新してから着手する）。

- **`list`**: `|`区切り・ヘッダなし・NULLは空文字列（フェーズ①からの既定挙動）。
- **`column`**: 列幅を値の最大幅（ヘッダ含む）に揃えて左詰め。**`.mode column`へ
  切り替えると`sqlite3`同様`.headers`が自動でonになる**（その後`.headers off`
  で個別に無効化できる）。ヘッダ行の下に`-`の下線行を出す。
- **`csv`**: RFC 4180。**行末は`\r\n`（CRLF）**——`sqlite3`の`.mode csv`と同じ
  （`list`等の他モードはLFのまま。CSVだけCRLFにするのはRFC 4180・多くの
  CSVパーサの慣習に合わせるため）。
- **`json`**: 行オブジェクトの配列。数値は数値型のまま、NULLは`null`。
  **BLOBは16進文字列にエンコードする**（生バイト列をJSON文字列へ直接
  埋め込むと、不正なUTF-8を`encoding/json`が黙って`U+FFFD`に置換し
  データが壊れるため）。
- **`line`**: 1列1行の`  name = value`形式（列名は右詰めで`=`の位置を揃える）、
  行の間に空行。

BLOB・NULL等の値の型判別は、`database/sql`から返る値の実際のGo型
（BLOB列は`[]byte`、TEXT列は`string`——実測で確認済み、
`.claude/rules/sqlite-quirks.md`参照）を型スイッチで見て行う。

## SIGINT（Ctrl+C）ハンドラの登録可否（フェーズ③Step 6）

REPLは、**標準入力が対話端末である場合に限り**Ctrl+C（SIGINT）用の
シグナルハンドラを登録する（`isInteractive`での判定）。パイプ・スクリプト
経由の非対話実行時はハンドラを一切登録せず、SIGINTの既定動作（即座に
プロセスを終了）をそのまま残す。

**理由:** 対話時はsqlite3準拠の中断コマンドとして扱いたい（クエリの中断・
入力破棄であり、無条件のプロセス終了ではない。詳細は`execdb_spec.md`§10
参照）が、これを非対話実行にも適用すると、**スクリプトから起動した
ExecDBをCtrl+Cで止められなくなる**という事故につながる（1回目のCtrl+Cが
「クエリ中断／入力破棄」として吸収されてしまい、スクリプトを止めたい
ユーザーの意図と噛み合わない）。対話/非対話でSIGINTの扱いを意図的に
変えている。

## ログ出力先

- ログ・診断メッセージは**標準エラー出力（stderr）のみ**とする。ログファイルの
  生成・ローテーション等の機構は持たない。
- REPLのクエリ結果は標準出力（stdout）に出力する。stdout（結果）と stderr（ログ・
  診断）は明確に分離すること。
- `--no-repl`（サーバーモード）稼働時の永続的なログ保存は、リダイレクトや
  Docker/systemd等の既存運用基盤に委ねる。ExecDB自体はログファイルを生成しない。
- `-q`/`--quiet` で出力自体を抑制できる。

## 起動時バナー

`.status`のような専用コマンドは設けない。代わりに起動時、バージョン・埋め込み
データの有無・スナップショット名・外部I/Fの待受状況・`--no-repl`かどうか等を
1度だけバナーとして表示する（`-q`/`--quiet`で抑制可能）。実行中に再確認したい
場合も、この情報が動的に変わることは想定しないため、専用コマンドを別途設けない。
バナーの具体的な表示例は仕様書§10参照。

## 保存確認プロンプト

`.exit`/`.quit` は、未保存の変更があっても**保存確認のプロンプトを出さず、
即座に終了する**（意図的な設計判断。詳細は仕様書 §3, §4 参照）。CI/CD等の
非対話実行との相性、および「保存は明示操作のみ」という原則を優先しているため、
確認プロンプトを追加する変更は行わないこと。

## サーバーモード（`--no-repl`）の停止・保存

REPLモードでは「保存は明示操作のみ、自動保存なし」が原則だが、サーバーモード
では `.snapshot`/`.overwrite` を打つ手段がないため、**例外的に**終了シグナル
（`SIGTERM`/`SIGINT`）受信時に自動保存してから終了する。この違いは意図的な
例外であり、矛盾ではない。

Windows のヘッドレス常駐（Windows Serviceとしての実行）時の正常終了は、
v1のスコープ外（既知の制限事項）として扱う。
